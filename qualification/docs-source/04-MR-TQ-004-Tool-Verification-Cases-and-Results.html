MR-TQ-003 §2 assigns the bulk of a TQL-5 effort to tool operational verification — requirements-based testing in the operational environment. This document is that verification, executed. Each of TOR-1 through TOR-11 (MR-TQ-002 §3) has at least one verification case with a defined input, an expected result, and a recorded result. Where the current source did not meet a TOR when MR-TQ-002 was written, the code change that closed it is identified by commit.

§1 Method and what counts as evidence

Verification is requirements-based: a case exists to demonstrate one TOR, not to exercise code for its own sake. Cases were executed by running the mcp-ratchet automated test suite (python -m pytest) against the repository at commit 907c8a9 on the environment recorded in §2. Three forms of evidence are cited:

  • Automated test cases — named tests under tests/, each asserting a specific TOR behaviour. These are the primary evidence for TOR-1 through TOR-7 and TOR-10.
  • Repository commits — for the three TORs whose verification required a source change (TOR-8, TOR-9, TOR-11), the commit that made the change, so the qualified behaviour is tied to an identified configuration item.
  • Real generated artifacts — for the TOR-8 and TOR-11 report markers, the check is run against an actually generated reports/dashboard.html and reports/drift-summary.json, per MR-TQ-003 §9 ("on a real generated report, not just the template source").
Not claimed here
This verification was performed by the tool's author. DO-330 expects verification independent of development (MR-TQ-003 §7). That limitation is unresolved and is carried to MR-TQ-005 as a condition on any real use of this material.

§4 Code changes this verification drove

Three of the eleven TORs did not hold against the source as MR-TQ-002 §4 recorded it. Each was closed by a change on the mcp-ratchet repository, before its verification case was executed, per the sequencing rule in MR-TQ-003 §4.

78d5971 — TOR-9 — load_baseline now returns a typed BaselineError (new dataclass in scanner/fingerprint.py, distinct from None) for a baseline file that is unreadable, unparseable, missing a required field, or an unsupported fingerprint_schema_version — instead of an unhandled JSONDecodeError/KeyError. server_side.on_list_tools gained a parallel baseline_error audit path alongside no_baseline. This is Fixes 1–3 of MR-TQ-003 §4.
a054e4a — TOR-8 and TOR-11 markers — audit_summary derives a per-target drift_status (latest session wins); is_clean is False whenever the latest session could not evaluate drift; the dashboard and detail page show a "DRIFT NOT EVALUATED" banner; a new reports/drift-summary.json sets drift_evaluation explicitly. The injection section gains a "not a qualified result" marker in all three report surfaces plus an injection_check field in the scan JSON. This is MR-TQ-003 §5.
907c8a9 — TOR-4 and TOR-5 coverage — the classifier cases MR-TQ-003 §9 calls for: tool_removed, input_schema change, annotations change, and a several-fields-at-once change (tests/test_drift_classification.py). No behaviour change — the classifier already handled these; the cases make the evidence explicit.

§6 Residual limitations

  • Independence. Author, verifier, and notional applicant are the same person. A real program must have verification performed independently of development. Carried to MR-TQ-005.
  • Scope boundary (unchanged). The fingerprint covers the Tool surface only. Resources, prompts, server-level instructions, and the content of tool-call results are not in the baseline and are covered by no TOR here. This verification does not extend the boundary — it is a real, scoped piece of future work (MR-TQ-002 §5).
  • Environment-bound. Verified only on Windows 10.0.19045 / CPython 3.13.5 / mcp 2.1.1. Any change to a row in §2 invalidates the result until re-verified. The SDK moved 2.0.0 → 2.1.1 since MR-TQ-002; the Tool model's client-visible field set was re-checked and is unchanged, and this is recorded rather than assumed.
  • Injection check not exercised live. The prompt-injection check needs ANTHROPIC_API_KEY for a real verdict; only its "key not set" path runs in this suite. It is outside the qualified function regardless (TOR-11).
  • "Latest session wins." drift_status reflects the most recent proxy session. A target with an old un-evaluated session but a working latest one reads as evaluated; the historical gap is retained as a count on the detail page, not surfaced on the card. Deliberate, and documented here.

What the review found — and what this revision did about it
The reviewer's verdict was "holds with minor caveats": five places where the "Recorded result" prose claimed more than the cited test literally asserted, each verified correct by source inspection but not by a test. This revision closes the three that a test can close:
  • TOR-10 — "byte-matches a direct connection" was backed only by a name+description comparison. Added test_forward_list_tools_is_byte_identical_to_direct, which serialises both tool lists with the fingerprint's canonical dump (all eight fields) and asserts equal bytes, and strengthened the call-tool test to compare against a real direct call.
  • TOR-3 / TOR-5 — the "nothing else drifted" / "one event per field" claims are now pinned by exact len(events) / exact event-set assertions, not just membership checks.
Two caveats are accepted as source-backed, not test-backed, and stated as such here: TOR-1's eight-field canonical enumeration (it is scanner/fingerprint.py's _TOOL_FIELDS tuple, read directly) and TOR-11's "the injection verdict never enters the drift result" (an architectural separation visible in the code, not exercised by a test). The SDK 2.0.0→2.1.1 field-set re-check (§2, §6) is likewise an author assertion with no cited artifact.

Post-revision the cited-file count is 45 and the full suite is 195; the reviewed-commit figures (44 / 194) are retained above as the record of what the independent pass actually re-executed. The reviewer noted that the §4/§5 independence condition — a named human reviewer on a real program — remains the governing open item; this pass was a cold re-execution and adversarial read, which substantively addresses "independent of development" but is not a substitute for program-level QA sign-off.
